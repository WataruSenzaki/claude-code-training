## サマリ

- 結論: 導入は「**Claude Code＝注目のコーディングエージェント → なぜ強いか（実際に手を動かす・段取り・量に強い）→ その強さは非エンジニアにも効く（コードも書類も "ファイル"）→ だから賢いチャットでなく実際に片付けるエージェント → こんなことができます（完成品イメージ）→ 本講義がそこまで連れて行く → 第一歩は土台＝契約**」の7節。
- 次のアクション: 「使うにはまず土台（有料アカウント）が要る」と腹落ちしたら [02_契約.md](./02_契約.md) へ。実際に手を動かすのは [03_セットアップ.md](./03_セットアップ.md) から。

## 構成（Mainline・7節）

> 出口ゲートは置かない（理由は「なぜこの構成か」）。手を動かさない動機＋理解パートで、到達を二値で測らない。成立の目安＝「『CC がどういう道具か』と『この研修がどこへ連れて行くか』が腹落ちし、次（契約）に進む気になっている」。
> 触る面: なし（手を動かすのは 03 から）。対象（誰が受けるか）で変わるのは完成品の例・刺し方だけ＝ Add-on（[add_on/00_index.md](./add_on/00_index.md)）。流れ自体は対象で変わらない。

| 節 | 伝えること | 核 | ねらい |
|---|---|---|---|
| 1. Claude Code＝注目のコーディングエージェント | AI にコードを書かせて開発作業を任せる "コーディングエージェント" として最前線で注目されている。**本来はエンジニア向けの道具**（ここを隠さない） | 正体＝コーディングエージェント。出自はエンジニア向け | まず正体を正直に置く。"汎用 AI" と薄めない |
| 2. なぜ強いのか | チャットが "言うだけ" なのに対し、CC は (a) 自分の環境で**実際に手を動かす**（ファイルを読み書き・コマンドを実行）、(b) 目標を渡すと**段取り→実行→確認まで自分で回す**、(c) **大量・多ファイルの作業に強い** | 優位＝やる／段取り／量 | "なぜコーディングで強いか" を3点で掴ませる |
| 3. その強さは、あなたにも効く | コードも書類も結局 "PC の中のファイル"。「ファイルを正確に・大量に・段取りして編集する」本業が、そのまま Excel・Word・PDF・データの仕事に効く。しかも**指示は普通の言葉でいい** | 橋＝コード仕事と書類仕事は同じファイル操作 | エンジニア向けの強さを自分事に接続する（導入の肝） |
| 4. だから「賢いチャット」ではない | 以上から CC の正体は「賢く答えるチャット」でなく「**実際に仕事を片付けるエージェント**」 | 結論＝実行するエージェント | 節1〜3 を一言で締め、完成品（次節）への期待を作る |
| 5. こんなことができます＝完成品イメージ | その結果できあがる物を見せる。L2 の成果物＝コマンド1つで `CLAUDE.md`（自分ルール）と `業務フロー.md`（自分の仕事の手順）がファイルで残る。**動く姿は見せず、できあがった物（静止）だけ** | 行き先＝残る成果物を具体物で | 抽象な強みを「手元に何が残るか」で着地させる |
| 6. 本講義の役割＝行き先まで連れて行く | この研修がさっきの完成品まで連れて行く。道のりは「**動く（土台）→ 自分用に育てる（橋渡し）→ 自分の仕事に当てる（自社業務）**」の3段。今いるのは入口 | 現在地＋道のり＝研修の役割 | 全体像を渡し、土台から始まる必然を受け入れやすくする |
| 7. 使うにはまず土台が要る → 契約へ | その第一歩＝土台（契約→セットアップ）。飛ばせない。だから次は契約から | 不可避性＝理解→手配の継ぎ目 | 次 Unit（契約→セットアップ）へ橋渡し |

前提条件: なし。導入は L1 の起点。受講者は「Claude Code を聞いたことがある／ない」のどちらでもよい。

## なぜこの構成か

- **コーディングエージェントの優位から入る理由**: 公式の肩書きは "agentic coding tool" ＝本来エンジニア向け。これを隠して "汎用 AI です" と薄めるより、強さの出自を正直に置いた方が説得力が出る。エンジニアを唸らせている実力を先に見せ、それを非エンジニアに橋渡しする順にした。
- **強みを「優位点（複数）」で見せる理由（旧「1点」からの変更）**: 旧版は「違いは1点＝ローカルファイルの読み書き」に絞ったが、公式定義では `edits files` と `runs commands` が対等に並び、さらに "plans → 実行 → verify" の段取り（エージェント性）が核。ファイルだけに矮小化すると CC の強さ（コマンド実行・多段・量）が落ちる。よって「実際に手を動かす／段取り／量」の優位点で見せる。※DESIGN.md の旧「1点」記述は要擦り合わせ。
- **節3（非エンジニアへの橋）を独立させた理由**: 「コーディングエージェント」と聞いた非エンジニアは「自分には関係ない」と離れやすい。離れる前に「コードも書類も同じ "ファイル"。本業がそのまま効く」と橋を架ける節を独立で置く。ここが導入の成否を分ける継ぎ目。
- **節2〜4 を語り、節5 で見せる順にした理由**: 節2〜4 は能力を "語る" 段。抽象のままだと腹落ちしない。直後に「こんなことができます」と残る成果物（具体物）を見せて着地させる。
- **完成品を L2（確定済み）に依存させた理由**: L3（自社業務）は試作中で未確定。未確定の下流に依存すると導入も揺れる。L2 の「スキルで業務フローをファイルに出す」核は固定なので、先見せの素材として安定する。
- **動く姿を見せず完成品（静止）だけにした理由**: ライブデモは時間と環境に左右され、失敗すると逆効果。導入は動機＋理解パートなので「残る物（成果物）」を見せれば足り、動かす体験は L2 以降に任せる（ライブは Add-on）。
- **本講義の役割（節6）を入れた理由**: 研修の入口を別 Layer（一度作った Compass）に切り出さず導入に一本化したので、「研修がどこへ連れて行くか」も導入が担う。完成品（行き先）を見せた直後に道のりと現在地を置くと、「土台から始まる」必然が腹落ちする。スコープの線引き（やる／やらない）は対象で変わりうるので Add-on 側に置く。
- **節7を「だから始めよう」でなく「土台が要る→契約」にした理由**: 「すごい→だから始めよう」は売り込みの因果で、動機を持つ受講者には効かない。成立する因果は不可避性＝「使うにはまず土台（契約→セットアップ）が要る、飛ばせない」。これなら理解→手配の継ぎ目として論理が閉じ、次章（契約）に具体的につながる。
- **出口ゲートを置かない理由**: 導入は手を動かさない動機＋理解パートで、到達点を二値（できた／できない）で測れない。03/04 のような「打てば応答する」ゲートを無理に当てると、動機づけ・理解が手続きにすり替わって逆効果。成立の目安は「次（契約）に進む気になっている」で十分とした。
- **触る面（CLI/デスクトップ/ブラウザ）を Add-on に逃がした理由**: ファイル操作・コマンド実行は CLI 固有でなくデスクトップアプリでも成立する（同一エンジン）。「違いがあるから CLI」は論理が通らない。触る面の違いは Add-on にし、構成は「正体 → 強み → 橋 → 完成品 → 役割 → 契約」に徹する。
