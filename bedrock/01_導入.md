## サマリ

* 結論: 導入は「**コーディングエージェントという正体 → チャットとの違い（代行者）→ コードも書類も同じファイル編集 → 手元に残る成果物 → 完成品までの道のり → まず土台が要る → 土台の全体像（契約・インストール・認証）**」の7節。手を動かさない動機＋理解パート。

* ゲート: **持たない**（動機・理解で二値で測れない。成立の目安＝次〔契約〕に進む気になっている）。

* 次のアクション: 「使うにはまず土台（有料アカウント）が要る」と腹落ちしたら [02\_契約.md](./02_契約.md) へ。実際に手を動かすのは [03\_セットアップ.md](./03_セットアップ.md) から。

## 1. 何を伝えるか（Mainline・7節）

> 出口ゲート: **置かない**。導入は手を動かさない動機＋理解パートで、到達を二値で測らない。成立の目安＝「『CC がどういう道具か』と『この研修がどこを目指すか』が腹落ちし、次（契約）に進む気になっている」。
> 触る面: なし（手を動かすのは 03 から）。対象で変わるのは完成品の例・刺し方だけ＝ Add-on（[add\_on/00\_index.md](./add_on/00_index.md)）。流れ自体は対象で変わらない。

| 節                                 | 伝えること                                                                                                                                                            | 核                          | ねらい                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------------------------- |
| 1. コーディングエージェントという正体      | AI にコードを書かせて開発作業を任せる "コーディングエージェント"。**本来はエンジニア向けの道具**（ここを隠さない）                                                                                                   | 正体＝コーディングエージェント。出自はエンジニア向け | まず正体を正直に置く。"汎用 AI" と薄めない          |
| 2. チャットとの違い（代行者） | チャットは聞けば "答える" だけ。CC は頼めば自分でやる＝**代行者**: (a) 自分の環境で**実際に手を動かす**（ファイルを読み書き・コマンドを実行）、(b) 目標を渡すと**段取り→実行→確認まで自分で回す**、(c) **大量・多ファイルの作業もこなす**                         | 違い＝CC は代行者（チャットは答えるだけ）     | チャットとの違い＝代行者だと掴ませる                |
| 3. コードも書類も同じファイル編集              | コードも書類も結局 "PC の中のファイル"。Excel・Word・PDF・データの仕事も、中身は「ファイルを正確に・大量に・段取りして編集する」こと＝CC の本業そのもの。しかも**指示は普通の言葉でいい**                                                        | 橋＝コード仕事と書類仕事は同じファイル編集      | エンジニア向けの強さを自分事に接続する（導入の肝）         |
| 4. 手元に残る成果物                       | その結果できあがる物を見せる。L2 の成果物＝コマンド1つで `CLAUDE.md`（自分ルール）と `業務フロー.md`（自分の仕事の手順）がファイルで残る。**動く姿は見せず、できあがった物（静止）だけ**                                                        | 行き先＝残る成果物を具体物で             | 抽象な説明を「手元に何が残るか」で着地させる            |
| 5. 完成品までの道のり                      | この研修がさっきの完成品まで案内する。道のりは「**動く（土台）→ 自分用に育てる（橋渡し）→ 自分の仕事でつかう（自社業務）**」の3段。今いるのは入口                                                                                    | 現在地＋道のり＝研修の役割              | 全体像を渡し、土台から始まる必然を受け入れやすくする        |
| 6. まず土台が要る                    | CC を使う第一歩＝土台。飛ばせない                                                                                                                                               | 不可避性＝理解→手配の継ぎ目             | 土台が要ることを腹落ちさせる                    |

## 2. なぜこの構成か

* **コーディングエージェントの優位から入る理由**: 公式の肩書きは "agentic coding tool" ＝本来エンジニア向け。これを隠して "汎用 AI です" と薄めるより、強さの出自を正直に置いた方が説得力が出る。エンジニアを唸らせている実力を先に見せ、それを非エンジニアに橋渡しする順にした。

* **代行の中身を3つ（手を動かす／段取り／量）で見せる理由**: 公式定義で `edits files`（ファイル操作）と `runs commands`（コマンド実行）が対等に並び、さらに "plans → 実行 → verify" の段取り（エージェント性）が核。だから1点に絞らず3つで見せる。

* **節3（非エンジニアへの橋）を独立させた理由**: 「コーディングエージェント」と聞いた非エンジニアは「自分には関係ない」と離れやすい。離れる前に「コードも書類も同じ "ファイル"＝書類仕事も同じファイル編集」と橋を架ける節を独立で置く。ここが導入の成否を分ける継ぎ目。

* **節2〜3 で語り、節4 で見せる順にした理由**: 節2〜3 は能力を "語る" 段。抽象のままだと腹落ちしない。直後に「完成品イメージ」と残る成果物（具体物）を見せて着地させる。

* **完成品を L2（確定済み）に依存させた理由**: L3（自社業務）は試作中で未確定。未確定の下流に依存すると導入も揺れる。L2 の「スキルで業務フローをファイルに出す」核は固定なので、先見せの素材として安定する。

* **動く姿を見せず完成品（静止）だけにした理由**: ライブデモは時間と環境に左右され、失敗すると逆効果。導入は動機＋理解パートなので「残る物（成果物）」を見せれば足り、動かす体験は L2 以降に任せる（ライブは Add-on）。

* **本講義の役割（節5）を入れた理由**: 研修の入口を別 Layer に切り出さず導入に一本化したので、「研修がどこを目指すか」も導入が担う。完成品（行き先）を見せた直後に道のりと現在地を置くと、「土台から始まる」必然が腹落ちする。スコープの線引き（やる／やらない）は対象で変わりうるので Add-on 側に置く。

* **節6を「だから始めよう」でなく「土台が要る→契約」にした理由**: 「すごい→だから始めよう」は売り込みの因果で、動機を持つ受講者には効かない。成立する因果は不可避性＝「使うにはまず土台（契約→セットアップ）が要る、飛ばせない」。これなら理解→手配の継ぎ目として論理が閉じ、次章（契約）に具体的につながる。

* **出口ゲートを置かない理由**: 導入は手を動かさない動機＋理解パートで、到達点を二値（できた／できない）で測れない。03/04 のような「打てば応答する」ゲートを無理に当てると、動機づけ・理解が手続きにすり替わって逆効果。成立の目安は「次（契約）に進む気になっている」で十分とした。

* **触る面（CLI/デスクトップ/ブラウザ）を Add-on に逃がした理由**: ファイル操作・コマンド実行は CLI 固有でなくデスクトップアプリでも成立する（同一エンジン）。だから触る面の違いは Add-on にし、構成は「正体 → 違い → 橋 → 完成品 → 役割 → 契約」に徹する。

* **土台の全体像（節7）を導入に置いた理由**: 契約・インストール・認証の概要を各 Unit の頭で繰り返すと冗長。導入で地図（3要素＋携帯比喩＋流れ）を1回渡せば、各 Unit は「前段との接続」を持たず詳細手順だけに集中でき、重複が消える。携帯比喩（契約＝サービス契約／インストール＝端末入手／認証＝端末と契約の紐付け）は非エンジニアに直感的。

* **認証とログインを層で分けた理由**: 認証＝概念（傘）、ログイン＝サブスク経路の手段。公式も "Authentication" の下に OAuth ログイン／API キー／クラウド認証を並べる。add\_on で手段が増えても概念名が壊れないよう、概念（節7）は「認証」、操作（03 段3）は「ログイン」と階層で語を分けた。
