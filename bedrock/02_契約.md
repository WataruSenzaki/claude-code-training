# 契約（ユニット）

> 用語スタック（各語は1階層だけを指す＝一意）:
> - **Bedrock** … L1（動く）の層
> - **ユニット** … 層の中身。標準で教えるユニットは番号付き。本ファイルはユニット「契約」
> - **Mainline / Add-on** … ユニットの中。Mainline＝外せない一本／Add-on＝標準外のおまけ（`add_on/` に置く）
> 対象が変わっても Mainline は不変・Add-on の選択だけが変わる（変更ダメージの局所化）。選ぶ行為＝構成。
> 前のユニット [01_導入.md](./01_導入.md)（なぜ CC か）から始まり、出口は次の [03_セットアップ.md](./03_セットアップ.md) の前提条件になる（ユニットの継ぎ目）。

## サマリ

- 結論: 契約の Mainline を「**有料プランの有効なアカウントを手元に持っている**」到達までの最小3段に確定。経路は**サブスク（Pro/Max）一択**で固定。API課金（従量）は分岐として Add-on に1本だけ逃がす。
- 件数: Mainline 3段／Add-on 4本／フィルタで除外2件。
- 裏取り: 無料プラン非対応・Pro/Max/Team/Enterprise・API課金（`ANTHROPIC_API_KEY` が優先）は公式で確認済（2026-05-29）。出典は末尾。
- 次のアクション: このアカウントで [03_セットアップ.md](./03_セットアップ.md) 段3（ログイン）が通る。契約の出口＝セットアップの入口（重複ではなく継ぎ目）。

---

## 1. Mainline（最小3段・サブスク経路）

> 出口ゲート: **「有料プラン（Pro か Max）が有効なアカウントを持っていて、ログイン情報が手元にある」**（二値・対象非依存）
> 触る面: ブラウザ（claude.com）固定。CLI はまだ触らない（触るのは 03 から）。唯一のパラメータ = プラン選択（Pro/Max）

| 段 | やること | 具体 | ねらい |
|---|---|---|---|
| 1. アカウント | Claude アカウントを作る（無ければ） | claude.com でサインアップ（メール／Google 等） | ログインの土台 |
| 2. 有料プラン | 有料プランを選んで契約する | **Pro（個人の標準）** または **Max（重い使い方）**。無料プランは CC 非対応 | CC を使える状態にする（ここが本体） |
| 3. 確認【ゲート】 | 有料が有効になっているか確認 | claude.com にログインでき、プランが Pro/Max 表示になっている | 03 のログインが通る状態を保証 |

### 確定事実（裏取り済み）

- **無料の Claude.ai プランは Claude Code 非対応**。最低でも Pro が要る
- 料金の目安: **Pro $20/月**、**Max $100 または $200/月**（重い使い方向け）
- サブスク経路の認証は CC 起動後の **`/login`（OAuth ログイン）が既定**（手順は 03 段3）
- **Team / Enterprise** は各シートに Claude Code が含まれる（個人契約でなく組織契約。非エンジニア汎用の Mainline には載せず、対象が組織なら構成で差し替え）

### 前提条件（Mainline ではない）

- なし。導入で動機が立っていれば始められる。**支払い手段（クレジットカード等）は受講者側で用意**

## 2. Add-on カタログ（目的タグ＋接続点）

> 目的タグは選別フィルタも兼ねる。「動機を強化するか／疑問を解消するか」のどちらでもない候補は、Add-on に入れない。
> 対象が変わったら、Mainline と Add-on の池はそのまま、構成で「どの Add-on を選ぶか」だけ変える。

| Add-on | 目的タグ | 接続点 |
|---|---|---|
| **API課金経路（従量）で使う**（Anthropic Console の APIキー。`ANTHROPIC_API_KEY` を立てるとサブスクより優先される。使った分だけ課金） | 疑問解消（別経路）＋動機（小さく試したい人向け） | 段2の分岐 |
| Pro と Max はどっちを選ぶ？（使う量で決める。迷ったら Pro） | 疑問解消 | 段2 |
| サブスク（plan）と API/Console は別課金（Pro を持っていても API は別払い） | 疑問解消（混同しやすい） | 段2後 |
| 支払い・解約まわり（月額・いつでも解約） | 疑問解消 | 段3後 |

### フィルタで弾いたもの（非エンジニア汎用に過剰／別領域＝Add-on に入れない）

- 第三者プロバイダ経由（Amazon Bedrock／Google Vertex AI／Microsoft Foundry）→ 組織のインフラ前提で非エンジニア汎用には過剰。対象が組織なら `add_on/` に作成
- ログインの実操作（`/login`・ブラウザ認証）→ [03_セットアップ.md](./03_セットアップ.md) 段3 の領域（契約はアカウントを用意するまで）

---

## 3. フラグ（非エンジニア向けで効く論点）

- **出口を「ログイン成功」でなく「有効なアカウントを持っている」に置いた理由**: 実際のログイン操作（`/login`・ブラウザ認証）は CLI を起動してから＝ [03_セットアップ.md](./03_セットアップ.md) 段3 の仕事。契約ユニットはブラウザで完結する「アカウントを用意する」までを担い、CLI に踏み込まない。これで触る面が混ざらない（契約=ブラウザ／セットアップ=CLI）。
- **「契約の出口＝セットアップの前提条件」は重複ではなく継ぎ目**: L1 は順序ありで、前ユニットの出口が次ユニットの入口になるのが正常（04 が 03 の出口から始まるのと同じ構造）。クリアしないと先に進めないのは当たり前で、それがユニットを分ける理由そのもの。
- **サブスクを Mainline・API を Add-on にした理由**: 非エンジニアの業務ユーザーには「月額で考えなくていい固定額（サブスク）」が既定として最も摩擦が少ない。従量課金（API）は「小さく試したい／組織の都合」がある人の分岐で、Mainline に置くと選択を迫られて止まる。経路が複数あること自体がこのユニットを独立させる価値。
