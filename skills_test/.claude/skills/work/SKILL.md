# work — 業務をまとめる（ラベル: 業務）

ユーザーの代表的な業務ひとつを聞き取り、`業務.md`（文章＝正本）にまとめるスキル。
ねらいは流れを写すことではなく、**手間と判断を見える形にして「ここを直せば楽になる」入口を作る**こと。

## この業務まとめに必ず残すもの（設計の核・自分では言わない）
- **薄い背骨（足場）**＝きっかけ〜終わりの流れ。これは主役ではない。判断と手間を貼る壁。
- **聞くのは3つ＝手間（量か煩雑か）／判断（何を達成したいから→こうする・誰が持つか）／属人（本人にしかできないか）**。ただし**置き場を分ける**:
  - 手間・属人 → 「手順の中身」の表（＝痛みの在処）
  - 判断 → **判断対応表に一本化**（＝暗黙知の置き場。手順の表には判断を書かない＝同じ判断を2つの表に重複させない）
- **判断対応表（主役）**＝暗黙の決めごとを「こうしたい → だからこうする → 今その判断を持つ人」で書き出したもの。
- **楽にする入口**＝一番重い手間と一番暗黙の判断を各1点だけ指す（改善案を量産しない）。

旧版の失敗＝全手順を平らに並べ、肝心の中身が1つの箱に潜って使えなかった。だから**背骨は薄く保ち、深掘りは「一番しんどい1手順」に集中する**。

## はじめに（毎回・自分では言わない準備）
- 同じフォルダに `業務.md` が既にあれば、最初に一度だけ聞く:「すでに業務のまとめ（業務.md）があります。新しく作り直しますか? それとも今のを直しますか?」（無ければそのまま進む＝何度呼んでも二重に作らない）。
- 同じフォルダに `会社.md` があれば読み、担当・業種に合わせて**例示だけ**寄せる（無くても普通に進む）。会社.md の中身を質問の代わりにはしない。

## 進め方の原則
- 相手は**非エンジニア**。専門用語も内部語（背骨／札／判断／属人）も画面に出さない。
- 候補を出して **はい/いいえ＋一言** で答えてもらう。長文は書かせない。迷っていたら例を足して助ける。
- 本人の言葉を勝手に変えない。**まとめる時は必ず確認を取る**（文章＝正本を本人が承認する）。

## 手順

### 1. 題材を1つ選ぶ（痛みで選ぶ）
次をそのまま表示する。
```
いつものお仕事で、「自分がいないと回らない」か「地味に手間がかかる」ものを1つ選んでください。
（例: 請求書の処理 / 見積もりづくり）
```
- **痛みのある業務を選んでもらうのが肝**。「楽な業務」「すでに誰でもできる業務」を選んだら、もっと手間や属人のあるものに寄せ直す。
- 複数の業務を語り始めたら「まずはこの1つに絞りましょう」と1業務に戻す。

### 2. 流れ（足場）をざっくり
```
始まりから終わりまで、やることを順にざっくり一言ずつ教えてください。
「まず◯◯、次に◯◯」のように。
```
出てきた手順を順に控える。**ここは深掘りしない（足場だから）**。段数だけ整える（本人の言葉は変えない）:
- **3段以下で粗い** → 一番大きい段を**1回だけ**割る:「その『◯◯』の中は、もう少し分けると何を?」（割りすぎない）
- **4〜7段** → そのまま使う
- **8段以上** → 束ね案を出す:「大きくまとめると『◯◯ → ◯◯ → ◯◯』ですね?」と**確認してから**採用。細部は手順4で拾う

### 3. 一番しんどい手順を1つ特定
```
この中で、一番 時間がかかる・気をつかうのはどれですか?
```
ここで挙がった手順を「重い手順」として、手順4で深掘りする（この業務まとめの本体はここ）。

### 4. 重い手順に3つの札を当てる（本体）
重い手順について、順に聞く。**一度に全部聞かず、はい/いいえ＋一言で1問ずつ**。

**(a) 手間（量か煩雑か）**
```
それは、数が多くて大変ですか? それとも、一個一個が細かくて気をつかいますか?
```

**(b) 判断（ここが最重要）**
```
そこでは、何を見て、どう決めていますか?
```
- 「指示書どおり」「マニュアルどおり」と返ってきたら、**判断は本人の外（上流）にある合図**。受け渡しへ遡る:
  ```
  その指示の中身（◯◯にするか△△にするか）は、誰がどうやって決めていますか?
  ```
- 出てきた決めごとを **「こうしたい・こういう時 → だからこうする → 今その判断を持つ人」** の形に言い換えて、はい/いいえで確認する。これが判断対応表の1行になる。
- 「いつもと違う対応は?」だけでは判断は出ない（それは実行のばらつき）。**「何を達成したいから、こうするのか」**を必ず取りにいく。
- 判断が複数出たら、表に複数行で残す。

**(c) 属人（本人にしかできないか）**
```
これ、今すぐ他の人に渡せますか? 渡せないなら、何がネックですか?
```
- ネックが「頭の中の決めごと」なら → 判断対応表で解ける。
- ネックが「特殊な手作業・道具」なら → 手間側の問題。
- どちらかを控えておく（「楽にする入口」で使う）。

### 5. 受け渡し（前後を軽く1問ずつ）
上流に判断が隠れていないかと、業務の境界を確かめる。
```
この仕事が来る前、誰が何を決めて渡してきますか?
```
```
最後に、何ができあがって、誰に渡しますか?（例: 承認済みの請求書を経理へ）
```
- 前の受け渡しで「達成したいこと→手段」の決めごとが出たら、それも判断対応表に足す。

## まとめて確認 → 書き出す
聞いた内容を下の形に並べて見せ、「**この内容で合っていますか? 楽にする入口はここ、で合っていますか?**」と1回だけ確認する。直しは本人の口頭指示で**文章を**直す（後で可視化もするが、直すのはいつも文章＝正本）。

確認できたら、今いるフォルダの `業務.md` に次の形で書く（見出しは固定。可視化する時の土台になる）。
```
# 業務: 請求書の処理

## 流れ（足場）
きっかけ: 請求書がメールで届いたら
1. 受領 → 2. 内容を確認 → 3. システムに入力 → 4. 上長に承認依頼 → 終わり: ファイルに保管

## 手順の中身（手間・属人）
| 手順 | 手間 | 属人 |
|---|---|---|
| 4 承認依頼 | 煩雑（金額で出し分け） | 金額基準が頭の中＝本人のみ |

## 判断対応表（主役）
| こうしたい・こういう時 | だからこうする | 今この判断を持つ人 |
|---|---|---|
| 50万円を超える請求 | 部長承認に回す | 自分（経験で覚えている） |

## 楽にする入口（1〜2点だけ）
- いちばん暗黙: 上の金額基準 → 表にすれば誰でも判断できる（属人が解ける）
- いちばん手間: 手順4（煩雑）→ 金額で自動仕分けできないか
```

- **「楽にする入口」は指すだけ**。一番重い手間と一番暗黙の判断を各1点。改善案を並べ立てない。
- 手順の中身の表（手間・属人）を埋めるのは**中身のある手順だけ**（重い手順）。判断はこの表に書かず**判断対応表へ一本化**する。空欄を作らない。

書き終えたら伝える:「`業務.md` ができました。一番下の『楽にする入口』が、この業務を楽にする出発点です。」

## 終わったら次へ進む（連鎖・受講者に操作させない）
`業務.md` が確定したら、受講者に `/draw` と打たせず、**そのまま続けて `draw` スキルを実行する**。先にこう一言だけ伝える:
「では、いまのまとめを図にしてお見せします。」
（draw は連鎖の終端。`業務.md` さえあれば後から単独でも呼べる＝単独再利用も可。）
