## 成果：配布スキルの設計

### 結論（どんな設計にしたか）
配布スキルを「単機能スキルの連鎖」に分割。受講者は1コマンドで起動し、
質問に答えるだけで“自分用フォルダ”に成果物が一式残る。

| スキル | 受講者ラベル | やること | 出力 |
|---|---|---|---|
| profile | プロフィール | 呼び方・口調・説明の出し方・進め方を聞く | CLAUDE.md（自分好みの振る舞いルール） |
| company | 会社 | 会社・自分の担当を短く聞く | 会社.md（自社の事実） |
| work | 業務 | 一番しんどい業務を1つ、流れ＋手間/判断/属人を聞く | 業務.md（しごとの地図） |
| draw | 可視化 | 業務.md を図に変換 | 1枚のHTML図（ブラウザ表示） |

### なぜこの設計にしたか
- **責務を分けた（SoC）**：対話で引き出す役と図に変換する役は別物。連鎖が1段増えることで
  Unit4「種明かし」が映える教材価値も乗る。
- **振る舞いと事実を分離**：CLAUDE.md（振る舞い）と 会社.md（事実）を別ファイルに。
  事実を振る舞いに混ぜない＝公式の「事実・頻繁に変わる情報は CLAUDE.md から除外」と整合。
- **連携は「あれば使う・無くても動く」**：連鎖の旨味（重複を聞かない）と単独再利用を両取り。
  各スキルが前段に強く依存せず壊れにくい。
- **model/view を分離**：文章（業務.md）が正本、図はその写し。直しは文章に対してだけ行い、
  draw は対話を持たない純変換に徹する。
- **業務は「線形の手順」でなく「しごとの地図」**：痛みベースで題材を1つ選ばせ、重い手順に深掘りを
  集中。暗黙の判断を「判断対応表」に外在化し、末尾に「楽にする入口」を1〜2点だけ示す。
- **方向性は裏取り済み**：As-Is可視化→ECRS という業務改善の定石と一致することを一次情報で確認。

### 比較対象（何と比べて選んだか）
- 当初構想（profile/scan で競合調査）↔ **受講者の業務に効く設計へ転換** …
  もとは profile（自分への振る舞い）＋ scan（会社情報をもとに競合を調査）を配る想定だった。
  だが (1) 競合調査はチャットAIでもできる＝わざわざ Claude Code を使う必然がない、
  (2) 研修後に持ち帰っても自分の仕事に直接効かず価値が薄い、の2点で断念。
  受講者自身の業務に効く profile / company / work / draw に作り直した。
- 1〜2スキルに統合 ↔ 連鎖に分割 … 単独再利用＋教材価値が、凝集のメリットを上回った。
- 線形の業務フロー ↔ **判断を引き出して残す設計** …
  手順を順に並べるだけでは、肝心の判断（何を見て・どう決めているか）が不明確なまま埋もれ、
  その先に進めない。判断を引き出して表に残す形に変えた。
- mermaid / CDN依存の図 ↔ 手書き HTML/CSS（JSゼロ）… 独自レイアウトが必要・社内NWやオフラインで
  CDNが落ちる・CC自身が mermaid を描けない。自己完結を取った。

### 得られるもの
- 受講者は答えるだけで、自分用フォルダに「振る舞いルール＋自社情報＋しごとの地図＋図」が一式残る。
  “自分の仕事が構造で見える”という中間の驚き。
- 暗黙知（判断）が表に出て属人が解ける入口、手間を減らす入口（ECRS）が示される。
- 各スキルは単独でも再利用可能で壊れにくい。L3「楽になる（CCが地図で一手やる）」への橋になる。
